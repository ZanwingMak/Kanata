# 05 · 测试文档

> 用例 ID 规则 `TC-<模块>-<三位序号>`，每条必须关联至少一个 `FR-*` / `NFR-*`。
> 执行结果记录在 `结果` 列：`PASS` / `FAIL` / `BLOCKED` / `N/A`，并注明版本号与日期。

---

## 1. 测试策略

| 层级 | 范围 | 工具 | 触发时机 |
| --- | --- | --- | --- |
| 单元测试 | 文件名解析、指纹计算、弹幕归一化、时轴换算、去重、屏蔽规则 | XCTest / Vitest | 每次提交 |
| 契约测试 | 网关 API 请求响应结构（对照 `02` 文档类型） | Vitest + JSON Schema | 每次提交 |
| **源探活测试** | 各平台适配器真实可用性 | CI 定时任务 | **每日 + 发版前** |
| 集成测试 | 媒体源接入 → 匹配 → 弹幕 → 渲染 全链路 | XCUITest / Playwright | 每日 |
| 性能测试 | 渲染帧率、内存、起播、弹幕加载 | Instruments / Chrome DevTools | 每周 + 发版前 |
| 兼容性测试 | 设备 × 系统 × 编解码 × 浏览器矩阵 | 手工 + 设备农场 | 发版前 |
| 无障碍测试 | VoiceOver、Dynamic Type、对比度 | Accessibility Inspector | 发版前 |
| 回归测试 | P0 用例全集 | 混合 | 发版前 |

**质量门禁（发版前必须全绿）**：P0 用例通过率 100%；P1 ≥ 95%；无 S1/S2 缺陷未关闭；性能指标全部达标；源探活报告中 P0 源全部可用。

## 7. 弹幕源探活自动化（关键）

平台接口是最不可控的外部依赖，必须自动监控。

### 7.1 机制

```
CI 定时任务（每日 02:00 + 每次发版前）
  for each provider in registry:
     ① healthCheck()：用固定的真实剧集 ID 拉一次弹幕
     ② 断言：HTTP 200 + 关键字段存在 + 条数 > 阈值 + 解析无异常
     ③ 记录：耗时、条数、错误码
  产出 sources-health.json + Markdown 报告
  任一 P0 源失败 → 告警（GitHub Issue 自动创建 + 标记 blocked-release）
```

### 7.2 探活断言表

| 源 | 探活对象 | 条数阈值 | 关键字段断言 |
| --- | --- | --- | --- |
| dandanplay | 固定 episodeId | >100 | `comments[].p` 为 4 段 |
| bilibili | 固定 cid | >100 | protobuf 可解析，`elems[].progress` 存在 |
| iqiyi | 固定 tvid | >50 | 解压后为合法 XML，含 `showTime` |
| qq | 固定 vid | >50 | `segment_index` 非空，`barrage_list` 存在 |
| mgtv | 固定 cid+vid | >20 | `data.items[].time` 存在 |
| youku | 固定 vid | >20 | 签名通过，`result` 可解析 |

### 7.3 失效响应流程

1. 探活失败 → 该源在 `/kanata/v1/sources` 标记 `available:false`；
2. 客户端自动跳过该源并在设置页显示状态，**不阻塞播放**；
3. 自动建 Issue，附最近一次响应前 512 字节（脱敏）；
4. 修复后更新 `03` 文档的「最后验证日期」。
