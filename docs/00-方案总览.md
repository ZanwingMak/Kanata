# 00 · 方案总览（需求扩展 + 技术选型 + 里程碑）

## 1. 原始需求与扩展

### 1.1 你提出的原始需求
1. 支持 iOS / iPadOS / Web / Apple TV 四端；
2. 支持自行导入视频资源（本地视频文件、NAS 资源等）；
3. 支持从不同视频平台（B 站、爱奇艺等）获取**同一内容**对应的弹幕；
4. 需要登录凭证的平台要提供登录方式；
5. 导入应用内播放并同步显示弹幕，体验对标弹弹play。

### 1.2 扩展后的产品定义

> **Kanata 是一个「自有片源 + 全网弹幕」的跨端播放器。**
> 它不提供任何影视内容，只把用户自己的视频，与互联网上公开的弹幕数据合并成一次观看体验。

原始需求向外扩展出 8 个必须补齐的能力域（否则产品不成立）：

| # | 扩展能力域 | 为什么必须有 | 对应需求 |
| --- | --- | --- | --- |
| E1 | **媒体库与刮削** | 用户导入的是一堆文件，没有剧名/季/集信息就无法匹配弹幕。需要文件名解析 + TMDB/豆瓣元数据 | FR-LIB-* / FR-MATCH-* |
| E2 | **智能识别与匹配** | 「同一资源」是全案核心难点：本地文件 ↔ 平台剧集的映射，需 hash + 文件名 + 时长三重策略 | FR-MATCH-* |
| E3 | **多源弹幕聚合与去重** | 一集内容可能同时存在于 B 站/爱奇艺/腾讯，需合并、去重、按源开关、按源着色 | FR-DMK-* |
| E4 | **时轴对齐（Offset/Scale）** | 各平台版本片头长度不同（正片版/含 OP 版/删减版），弹幕会整体错位，必须能校正 | FR-SYNC-* |
| E5 | **弹幕渲染引擎** | 需要 60fps、防重叠、多轨道、蒙版（人像不挡）、密度控制、屏蔽词，tvOS 4K 下尤其吃性能 | FR-DMK-1xx |
| E6 | **凭证与登录体系** | B 站需 Cookie 才能拿完整弹幕/港澳台内容，需扫码登录 + Keychain 存储 + 过期续期 | FR-AUTH-* |
| E7 | **跨端同步** | 四端共存，观看进度/弹幕配置/媒体库/匹配结果需同步（iCloud 或自托管） | FR-SET-* |
| E8 | **端差异适配** | tvOS 无本地文件系统、只能遥控器操作；Web 受 CORS/编解码限制，不能直连 SMB | FR-TV-* / FR-WEB-* |

### 1.3 目标用户与典型场景

- **主场景 A（家庭 NAS 党）**：Synology / Emby 上有整季番剧或剧集，在 Apple TV 上打开就能看到满屏弹幕。
- **主场景 B（本地文件党）**：iPad 上从 Files / iCloud 导入 MKV，自动匹配到弹弹play + B 站弹幕。
- **主场景 C（找不到官方源）**：动画只有 B 站有弹幕、剧集只有爱奇艺有弹幕，需要跨平台聚合补齐。
- **反场景（不做）**：在线追剧、下载资源、视频解析、社区/社交。

## 2. 系统方案

### 2.1 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│ 表现层                                                       │
│  iOS/iPadOS App    tvOS App        Web App                  │
│  SwiftUI            SwiftUI(焦点)   React + ArtPlayer        │
├─────────────────────────────────────────────────────────────┤
│ 客户端共享层（Apple 端 = Swift Package「KanataCore」）        │
│  媒体库 / 匹配 / 弹幕客户端 / 时轴 / 凭证 / 播放抽象 / 缓存    │
├─────────────────────────────────────────────────────────────┤
│ 服务层  Kanata Gateway（Node/TypeScript，Docker 可自托管）    │
│  识别归一 → 平台适配器 → 弹幕归一化 → 缓存 → 兼容层输出       │
├─────────────────────────────────────────────────────────────┤
│ 外部依赖                                                     │
│  弹弹play 开放平台 / 各视频平台公开接口 / TMDB / 豆瓣          │
│  用户的 NAS：SMB · WebDAV · Jellyfin/Emby/Plex · DLNA        │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 为什么要有网关（核心架构决策）

不做网关的代价：每个平台的接口签名、分片规则、压缩格式都要在 Swift 和 TypeScript 各写一遍；平台一改版，四端全部要发版，App Store 审核 1–3 天不可接受。

有网关的收益：
1. **平台易变性隔离** —— 逆向逻辑只在一处，改完立即生效；
2. **跨端一致** —— Swift/TS 只实现一个 HTTP 客户端；
3. **生态兼容** —— 对外走弹弹play v2 接口规范，用户可以直接把现成的 `danmu_api` 服务填进来当数据源，也可以把 Kanata 网关填进 Senplayer / EPlayerX 等第三方播放器；
4. **合规可切换** —— App Store 版本可只带官方源，自托管网关承载全部适配器（见 DEC-02）。

### 2.3 技术选型

| 层 | 选型 | 理由 | 备选 |
| --- | --- | --- | --- |
| Apple 端 | Swift 6 + SwiftUI，三端共享 `KanataCore` SPM 包 | tvOS 只有原生方案成熟；弹幕渲染需要 Metal/CADisplayLink 级控制 | — |
| 播放内核 | AVPlayer（H.264/HEVC/HLS，享硬解、PiP、AirPlay、字幕）+ VLCKit（MKV/DTS/特殊编码兜底），运行时按探测结果择一 | 单一内核无法同时满足体验与格式覆盖 | KSPlayer（Swift 原生 FFmpeg 封装，作为 VLCKit 备选） |
| 弹幕渲染 | 自研引擎：`CADisplayLink` 驱动 + Metal 纹理批渲染（tvOS/iPad 4K）；文本预排版缓存 | 现成库（BarrageRenderer 等）无 tvOS/4K 优化，且不支持蒙版 | SpriteKit（快速原型可用） |
| Web 端 | TypeScript + React + Vite + **ArtPlayer + artplayer-plugin-danmuku**（含 mask 插件） | 弹幕/HLS/字幕开箱即用，插件生态完整，MIT | Video.js + 自研弹幕层 |
| 网关 | Node 20 + TypeScript + Fastify（Docker/Vercel/Cloudflare 均可部署） | 与 `danmu_api` 生态同构，便于借鉴与互操作；I/O 密集型场景合适 | Go（性能更好，生态参考少） |
| 缓存 | 网关：内存 LRU + 可选 Redis；客户端：SQLite(GRDB) / IndexedDB | 弹弹play 要求缓存 2–24h，平台接口也需限流保护 | — |
| 元数据 | TMDB（主）+ 豆瓣（中文补充）+ 弹弹play 番剧库 | 中文影视命名归一化必须有中文源 | — |
| 跨端同步 | CloudKit（Apple 端）+ 网关可选账号态（自托管场景） | 免服务器成本，隐私友好 | — |

### 2.4 核心链路：从「一个文件」到「一屏弹幕」

```
①  用户导入源  ──►  ②  扫描 & 刮削  ──►  ③  生成识别指纹
   SMB/WebDAV        文件名解析          文件名 + 前16MB MD5
   Jellyfin/Emby     TMDB/豆瓣           + 文件大小 + 时长
   Files/iCloud      季集号推断
                                              │
                                              ▼
⑥  渲染 & 播放  ◄──  ⑤  归一 & 对齐  ◄──  ④  多源匹配
   多轨道防重叠        统一模型            弹弹play /api/v2/match
   蒙版/降密/屏蔽      去重 + 着色          B站 season → cid
   Offset 实时可调     Offset/Scale        爱奇艺 tvid、腾讯 vid…
```

**难点排序（工程风险从高到低）**：
1. ④ 跨平台剧集映射准确率（中文剧名别名多、季集编号混乱）；
2. ⑤ 时轴对齐（片头差异导致整体偏移，用户感知极强）；
3. ⑥ tvOS 4K 弹幕渲染性能；
4. ③ tvOS/Web 上无法读取整文件做 hash（需分段 Range 请求）；
5. 平台接口易变性（优酷 MTOP 双层签名最脆弱）。

### 2.5 时轴对齐方案（E4 展开）

三级策略，逐级自动化：

1. **手动偏移**（必做）：播放中 ±0.5s 步进调整，按「剧名/季/集」三级粒度记忆，同一季自动继承。
2. **时长比缩放**（必做）：`scale = 本地时长 / 平台时长`。差异 >1% 时启用线性缩放，解决帧率/剪辑版本差异。
3. **弹幕密度互相关**（进阶，M3）：把两个源的弹幕密度采样成 1Hz 曲线，做互相关求峰值 → 自动估计偏移。同一集在不同平台的「名场面」密度峰值高度一致，实测可把误差压到 ±2s 内。无需音频指纹，纯数据侧计算，成本低。

### 2.6 里程碑

| 里程碑 | 目标 | 交付 |
| --- | --- | --- |
| **M0 · 基线** | 打通「本地文件 + 弹弹play 弹幕」在 iOS 上的最小闭环 | iOS App 可播放本地 MKV 并显示弹幕 |
| **M1 · 源接入** | SMB / WebDAV / Jellyfin / Emby / Plex 接入；媒体库与刮削 | iOS + iPadOS |
| **M2 · 网关与多源** | 网关上线，B 站/爱奇艺/腾讯/优酷/芒果适配器；凭证与扫码登录；手动 Offset | 全平台弹幕聚合可用 |
| **M3 · 全端铺开** | tvOS App、Web App；自动时轴对齐；弹幕蒙版；跨端同步 | 四端齐全 |
| **M4 · 稳定性** | 源健康监测与自动降级、性能调优、无障碍、错误恢复 | 可长期维护形态 |

## 3. 弹幕资源获取渠道总览

完整参数与实现细节见 `03-弹幕源适配矩阵.md`，此处为决策级摘要。

| 来源 | 获取难度 | 是否需凭证 | 覆盖内容 | 采纳 |
| --- | --- | --- | --- | --- |
| **弹弹play 开放平台** | 低（官方 API，需 AppId/AppSecret） | 应用级密钥 | 番剧为主，文件 hash 精准匹配 | ✅ 主力 / 默认源 |
| **哔哩哔哩** | 中（protobuf 分片） | 建议（SESSDATA，否则弹幕不全、无港澳台） | 番剧、影视、UP 主投稿 | ✅ |
| **爱奇艺** | 低（按 tvid 分桶的 zlib 压缩 XML） | 否 | 剧集、综艺、影视 | ✅ |
| **腾讯视频** | 中（base 取分片索引 → segment 拉 JSON） | 否 | 剧集、综艺、影视 | ✅ |
| **芒果 TV** | 低（cid+vid，返回中带 next time） | 否 | 综艺强项 | ✅ |
| **优酷** | 高（阿里 MTOP，`_m_h5_tk` + 双层 MD5 签名） | 否（需 token cookie） | 剧集、动漫 | ✅（标注为易失效） |
| 巴哈姆特动画疯 | 中 | 否 | 繁中动画 | ⭕ 可选 |
| 咪咕 / 搜狐 / 乐视 | 低–中 | 否 | 补充 | ⭕ 可选 |
| 第三方聚合 API（如 `danmu_api` 公共实例） | 极低（填 URL 即可） | 否 | 取决于实例 | ✅ 作为「自定义源」兜底 |

## 4. 视频资源导入渠道总览

完整细节见 `04-视频源接入矩阵.md`。

| 渠道 | iOS/iPadOS | tvOS | Web | 说明 |
| --- | --- | --- | --- | --- |
| 本地文件 / Files / iCloud Drive | ✅ | ❌（无文件系统） | ✅（File API 选择） | iOS 走 `UIDocumentPicker` + 安全书签 |
| iTunes 文件共享 / AirDrop | ✅ | ❌ | — | 沙盒 Documents |
| **SMB / CIFS** | ✅ | ✅ | ❌（浏览器不支持） | NAS 最常用，走 VLCKit/自研 SMB 客户端 |
| **WebDAV** | ✅ | ✅ | ⚠️ 需 CORS 或网关代理 | Synology / 坚果云 / Alist |
| FTP / SFTP | ✅ | ✅ | ❌ | 兼容旧设备 |
| NFS | ⚠️ 依赖内核库 | ⚠️ | ❌ | 低优先级 |
| **Jellyfin / Emby** | ✅ | ✅ | ✅ | 官方 REST API，自带元数据，**推荐首选** |
| **Plex** | ✅ | ✅ | ✅ | REST API + Plex Token |
| **Synology DSM**（File Station / Video Station） | ✅ | ✅ | ✅ | DSM Web API，含官方登录 |
| Alist / OpenList | ✅ | ✅ | ✅ | 统一网盘聚合，HTTP 直链 |
| DLNA / UPnP | ✅ | ✅ | ❌ | 老设备兜底 |
| HTTP(S) 直链 / m3u8 | ✅ | ✅ | ✅ | 用户自有直链 |
| 局域网内建 HTTP 服务（App 自带） | ✅ | 接收端 | — | 手机/电脑推送到 Apple TV |

**tvOS 的关键结论**：Apple TV 没有用户可见文件系统，**所有片源必须来自网络协议**。因此 SMB / WebDAV / Jellyfin 的实现优先级在 tvOS 上高于一切，M1 就要做。

## 5. 开放问题（不阻塞开发，按推荐值先行）

1. 是否需要「发送弹幕」到第三方平台？→ 一期不做（DEC-06），仅支持本地自建弹幕（写入本地库，跨端同步）。
2. 是否需要账号体系？→ 一期不做，配置走 iCloud 同步。
3. 是否支持字幕外挂 / ASS 特效字幕？→ 需要（用户预期强），M2 以 libass 方案纳入。
4. Web 端是否需要转码？→ 不做转码，浏览器不支持的编码提示用户改用 Apple 端。
